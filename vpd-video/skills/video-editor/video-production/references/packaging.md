# Thumbnails and social copy

This reference applies to final video packages. Transcript-only tasks, brainstorms, rough animatics and music auditions do not require final covers or post copy; use [review delivery](review.md) for those video previews. Timed video captions are a separate final deliverable from the post copy below. Include an SRT or WebVTT for every selected layout and normally a burned-in captioned export for socials. Follow [caption review](editing.md#captions) and record reviewed sidecars in [the manifest](package.md).

## Covers

By default, every requested aspect gets a usable cover, even if the request only said “edit this video.” Honor an explicit exception recorded in the brief and manifest. Reuse approved artwork for a revision when it still matches.

For recorded-person videos, choose a sharp real frame with open eyes and a natural expression. For animated videos, use accepted artwork or a representative rendered scene. Preserve identity and existing redactions. A short hook should express the actual promise. Favor few words, large type, strong contrast and generous margins.

Use approved covers and the current brief as style references. Keep an individual creator's palette and preferences in their supplied private profile. Use screenshots as evidence, not invented product features. Check readability at phone size and recompose portrait covers instead of clipping landscape art.

Use available image generation/editing tools and the relevant image skill. If that capability is missing, report it and continue independent work; do not silently omit the cover. A selected frame with designed type is appropriate when requested or supported. Save final assets in the production directory.

## Copy

Use the creator's established voice, approved examples and brand guidance. Apply the project's own style checks; don't impose the skill author's punctuation, humor or model preferences. Keep copy concrete and faithful to the final result. Do not invent metrics, endorsements or audience promises. Use a relevant available writing skill when useful, without making it a package dependency.

| Destination | Deliverable |
| --- | --- |
| YouTube | Interesting, searchable title; description with the result, workflow and verified links. |
| YouTube Shorts | Its own title and concise description for the actual vertical edit. |
| Instagram | Editorial title/cover hook and independently pasteable caption. |
| TikTok | Editorial title/cover hook and short conversational caption. |
| LinkedIn | Editorial hook and a first-person post about what the creator did and why it helped. |
| Threads | Editorial hook and conversational short post. |
| Bluesky | Editorial hook and compact standalone post. |
| X | Editorial hook and compact standalone post. |

An editorial hook is not a claim that a platform has a separate title field. Use explicit filenames such as `youtube-title.txt`, `youtube-description.txt`, `instagram-hook.txt`, and `instagram-caption.txt`. Do not prepend a hook that the caption already includes.

Use a few relevant hashtags where useful. Avoid identical paragraphs everywhere. Do not promise replies, giveaways, “link in bio,” or “comment for the link” without an existing path and the user's direction.

When speech promises a workflow download, prepare a shareable artifact and track the missing public URL in setup notes. Keep local paths and placeholders out of paste-ready copy. A local ZIP is ready to share, not a hosted URL. Distinguish demonstrated features from ideas still being explored.

Platform limits, scheduler fields and account connections change. Verify these at publishing time using current official information or connected UI; don't hard-code assumptions from an older session.

Save a combined copy document plus clean per-platform files. The manifest associates each target with a real video, cover, title, description/caption and copy file. Keep asset readiness separate from publication status. Log shipped or scheduled content only after actual confirmation.

## Authorized publishing

Delivery alone does not authorize uploading, publishing or scheduling. Act on explicit authorization already present in the session; do not ask again for the same action. Use the authorized destination/account, copy and selected media candidate.

Before submitting, verify the upload master's actual container, video/audio codecs, dimensions, frame rate and duration against the destination's current requirements. Check current title, description and caption limits using official documentation or the connected service; do not reuse stale per-platform limits. A local player accepting a file does not establish platform eligibility. Preserve the edit master and create a compatible upload derivative when needed.

For scheduling, state/read back the destination, account, selected version, date, time and timezone so the user can see exactly what is being scheduled. Resolve missing material choices, but do not turn an already clear authorized schedule into a redundant approval gate. Confirm the service's returned schedule/status and record its identifier before reporting success. Avoid duplicate submissions if a response is uncertain; inspect the existing job first.

After a publish attempt or when an authorized scheduled job reaches its publication time, inspect the service's result for failed uploads, rejected media, incomplete processing or failed publication. Claim published only with an actual platform/service confirmation and URL when available. Record failures and the safe next action; do not leave a failed job labeled scheduled or published.

A future job's post-time check may still be pending when this task ends. Report that limit and the scheduled job ID. Do not silently create a watcher, reminder or recurring/background automation to check it; use one only when the user has requested that follow-up. A reminder is not a scheduled post.
